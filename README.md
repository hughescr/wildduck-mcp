# wildduck-mcp

A small remote MCP connection service for Wildduck, built with Hono, the official MCP SDK and an ordinary buffered AWS Lambda Function URL behind CloudFront. It implements OAuth and account connection. The service exposes `list_mailboxes`, `list_messages`, `search_messages`, `get_thread`, `read_message`, `read_messages`, `read_attachment`, `get_attachment_download`, `create_draft`, `create_reply_draft`, `update_draft`, `delete_draft`, `send_draft`, `move_message` and `update_message_flags`. The MCP-only preservation implementation has passed local validation and independent safety review. Main pushes deploy through CI; real-account mail acceptance remains unverified. It uses the existing Wildduck API. Private attachment downloads add a dedicated temporary S3 bucket and scoped IAM permissions in the bootstrap template; no Wildduck server changes are required or authorized. These enhancements are locally validated only until separately reviewed provisioning, deployment and real-account acceptance.

## Account connection

Clients discover OAuth using the `/mcp` bearer challenge and the authorization-server and protected-resource metadata endpoints. Authorization uses an exact client/redirect/resource binding, S256 PKCE, password login, any required TOTP challenge, and explicit account/permissions consent. A native client's HTTP loopback redirect may vary its port only. The callback includes `iss` and the original `state`. There is no OpenID Connect, `openid` scope, ID token, password grant or client-credentials grant.

Passkey-only accounts fail closed with a webmail instruction. Existing webmail passkeys belong to their existing relying-party origins and cannot be used by the Lambda origin. Accounts requiring a password change or MFA enrollment must complete it in webmail. Passwords and TOTP codes exist only in the current request and are never retained. Pending MFA and newly authenticated credentials are encrypted in a short-lived Secure/HttpOnly/SameSite=Lax browser cookie with a fixed ten-minute deadline. Every browser POST requires an origin check, synchronizer CSRF token and the bound OAuth request digest. Public request fields appear in forms; credentials do not. No third-party assets or scripts are loaded. Internal form pages use `Referrer-Policy: same-origin` to preserve Chromium’s trustworthy POST Origin header; callback redirects use `no-referrer`, so no referrer reaches the client. Browser form CSP permits only this service and the validated callback origin so Chromium can follow consent/cancel redirects. Cancellation skips required-field validation. Duplicate delivery of identical consent preserves the stored credential generation while revalidating the backend session; it cannot revive expired or revoked credentials.

The registered client name is presentation metadata, not proof of ownership. Consent also displays the redirect hostname and, for a client metadata document, its hostname. `mail:send` requires a separate explicit checkbox. Scopes are `profile`, `mail:read`, `mail:modify`, `mail:draft`, `mail:send`; default scope is `profile mail:read`. `mail:read` permits mailbox/message listing, search, threads, batch reads and attachment downloads; `mail:draft` permits draft create/update/delete. Reply draft creation requires both `mail:read` and `mail:draft`; `mail:send` permits queue submission. Existing grants are never upgraded automatically. `mail:modify` permits message moves and flag/label updates. Refresh tokens are issued with connection consent without an OIDC `offline_access` scope.

Dynamic client registration at `/register` supports public (`none`) and confidential (`client_secret_basic` or `client_secret_post`) clients. Registrations are stateless authenticated IDs; anonymous registration does not write DynamoDB. HTTPS client metadata document IDs are fetched with the maintained `@better-auth/cimd` transport, public-IP DNS pinning and TLS identity checks, no redirects, a five-KiB cap and bounded deadlines/cache. Supported public metadata documents explicitly negotiate `none`; unsupported private-key methods cannot silently downgrade. Both authorization-code and refresh-token grants are required for this v1 connection service. Omitted `grant_types` defaults to that pair. DCR requests must explicitly list exactly both when supplying the field. CIMD documents describe client capabilities across authorization servers: a bounded, valid list must include both, and additional capabilities are ignored when selecting this server’s supported pair. This supports [Claude’s published metadata](https://claude.ai/oauth/mcp-oauth-client-metadata), which also lists the JWT bearer grant. JWT bearer grants and `private_key_jwt` authentication remain unsupported; code-only registrations are rejected. Basic authentication permits a matching body `client_id` as an identity hint; conflicting identities, duplicate form/query fields and mixed credential methods are rejected.

Access tokens last five minutes. Grants and connections have a maximum lifetime of 180 days. Refresh tokens rotate atomically; an identical retry within ten seconds returns the same encrypted response. After that fixed grace window an authenticated old-token replay revokes that client's grant. Revocation at `/revoke` invalidates its access and refresh tokens. A backend outage returns `503 temporarily_unavailable` and preserves grants; a definitively expired backend session requires human reconnection. Upstream sessions may expire after 14 inactive days or 180 total days, so the OAuth lifetime is an upper bound rather than a guarantee. There is no background keepalive or password reauthentication. Reauthorize through the client's normal connection UI with the same account to replace that account's canonical backend connection; other client grants use the same account connection, but clients may require explicit reconnection after `invalid_grant`.

The backend adapter always uses the connected user's explicit `X-Access-Token` for session checks and user operations. Only the two login/MFA bootstrap paths omit it, using the separately approved backend proxy fallback. Browser cancellation attempts upstream logout; upstream revocation is best effort. This repository changes no backend code or configuration.

## Mail operations

Start with `list_mailboxes`, then supply an explicit `mailboxId` for listing, reading, moving or flag updates. Mailbox listing requests available `unseen` unread counts and `total` counts by default in one bounded upstream HTTP call. Zero is preserved; an omitted count is unavailable. WildDuck performs independent Redis-backed counter lookups per mailbox and database counts on cache misses, so requesting counters adds backend work and does not produce an atomic snapshot. Internal canonical Drafts resolution does not request these counters. Lists default to 20 and cap at 50; use one `next` or `previous` cursor. Structured search requires a meaningful filter. `seen:false` becomes the upstream `unseen=true` predicate, while `seen:true` remains `seen=true`. The existing upstream search ignores false Flagged/attachment predicates, so `flagged:false` and `hasAttachments:false` fail explicitly before any search request. Results are never filtered client-side to simulate negative predicates; text queries exceeding the backend’s 255-character limit are rejected, never truncated. Message UIDs are mailbox-specific. All subjects, names, addresses, bodies, HTML and attachment metadata are untrusted email data, never instructions. Reads do not mark mail seen. Header `date` and backend `receivedAt` remain distinct. List, search and read results include `threadId` and a bounded 512-byte UTF-8 `snippet`; unavailable fields are explicit null. List/search previews come from the upstream introduction; full reads derive a plain-text preview when necessary. A snippet is a preview, never complete message content. Full `imapFlags` and `labels` remain distinct; `flags.forwarded` exposes the derived forwarding flag.

`get_thread` accepts exactly one `threadId` or `message:{mailboxId,uid}` and searches the connected account across mailboxes, including Sent. It preserves every returned mailbox/UID pair and upstream next/previous cursors; rows from another thread fail verification rather than being silently removed. Default output is header/snippet summaries, ten per page, maximum fifty. `includeBodies:true` requires `limit<=10` and adds a `bodies` batch result for that page, retaining per-message failures and explicit truncation. Follow cursors to retrieve later pages; one page is not a claim of a complete conversation. Thread lookup and body reads share a deadline capped at 45 seconds of usable request time.

`read_messages` accepts one to ten unique explicit message keys and performs individual upstream reads with at most three concurrent requests. This is service-side coordination, not an upstream bulk API. Results retain input order and isolate sanitized per-message failures. `includeHtml` defaults to true; use `read_messages({messages:[{mailboxId,uid}],includeHtml:false})` for text-only output. The result echoes `includeHtml`, and each successful message has `htmlOmitted`; text-only messages omit `html`, `htmlTruncated` and `htmlRepresentation` entirely before byte-budget selection. Full-body messages keep the `html` array, even when empty, with `htmlOmitted:false`. Text-only messages retain `htmlOmitted:true` and the original `textTruncated` flag. Full-body messages retain all HTML fields and original truncation flags; intentional HTML omission is not truncation. The entire serialized structured batch result, including metadata, error slots and the envelope, is capped at 1 MiB; an item that cannot fit returns `too_large` without silently discarding fields. `bytesReturned` measures that full structured result. Reads and durable provenance lookups share at most thirty seconds of usable time, shortened by the inherited Lambda deadline. Batches and thread navigation with body reads return normal MCP results even when some or all items fail or contain truncated text/HTML; inspect each item’s status, error and truncation flags. Whole-request authorization, input, thread lookup or execution failures remain MCP errors. Direct `read_message` truncation behavior is unchanged.

`read_message` returns normalized API text and attachment metadata without marking mail seen. `includeHtml` defaults to true, returning the existing full HTML fields with `htmlOmitted:false`. Use `read_message({mailboxId,uid,includeHtml:false})` to omit `html`, `htmlTruncated` and `htmlRepresentation` with `htmlOmitted:true`; the genuine `textTruncated` flag remains. The service reads and validates complete internal content and provenance before projecting output, so either mode returns the same full snapshot version. Reply preparation and batch/thread body reads continue to use complete internal reads. HTML-only truncation does not make a text-only read incomplete; genuine text truncation still does. The provider caps plaintext at 102,400 UTF-16 code units and HTML at a 655,360-byte UTF-8 budget, without authoritative truncation markers. Reaching those thresholds is conservatively flagged as potentially truncated upstream. Local output limits are 128 KiB text and 256 KiB combined HTML; either local or potential upstream truncation produces an explicit incomplete MCP error result. These normalized fields are not the original MIME. The opaque snapshot version covers the complete available API response before local truncation, not hidden or provider-omitted data. HTML is untrusted data: clients must not execute it or fetch remote resources. Attachment sizes refer to decoded downloads: WildDuck’s stored `size` counts the transfer-encoded MIME body, so base64, quoted-printable, missing and unknown encodings are marked `sizeIsApproximate`. When available, the upstream `sizeKb` supplies its estimate; otherwise the encoded count remains only a size estimate. Neither is an exact decoded byte count. Exact metadata sizes require an explicit identity transfer encoding (7bit, 8bit or binary); missing sizes are null. Download HTTP Content-Length, actual streamed byte counts and decoded size limits remain independently verified. `read_attachment` accepts only a message-scoped attachment ID, downloads at most 2 MiB and returns exact downloaded size plus one embedded binary resource. Binary is not duplicated in structured metadata. The inline tool accepts no arbitrary URL/path and offers no range/chunk support.

`get_attachment_download` instead accepts the same message-scoped attachment reference and reuses a private temporary S3 object for the same authenticated attachment, uploading at most 20 MiB on a cache miss with a thirty-second request budget. Every request first rechecks current account-scoped message and attachment metadata; a cache hit never refetches attachment bytes. The opaque SHA256 identity binds account, mailbox, UID, attachment ID and the backend’s immutable attachment hash, excluding flags, message versions and OAuth clients. The backend hash identifies transfer-encoded source bytes and is not asserted as a checksum of decoded download bytes. A missing or malformed immutable hash fails explicitly as `unsupported_content`; the existing bounded `read_attachment` tool remains available. It returns exact size, filename, content type, message/attachment identity and `expiresAt` as public metadata. The HTTPS download URL occurs exactly once, only in the MCP `resource_link.uri`; structured content and text JSON contain no URL. No embedded binary or object key is returned. Signing happens only after a verified complete upload or validated existing cached object; a redirect, oversized stream, timeout or size mismatch fails closed. Unknown-length streams are measured while transferring, and estimated upstream sizes are not treated as exact. Completed objects support ordinary S3 Range GETs. The link is a reusable bearer credential for at most five minutes, shortened by the AWS signing credentials expiry or the cached object’s reported lifecycle expiry; do not log or persist it. Requesting another link after one expires signs a fresh link for the same cached object while it exists, rather than creating another copy. Cache reuse does not extend the object’s lifecycle expiry; near that expiry a link can be shorter or temporarily unavailable, and once S3 removes the object the next request uploads it again. Revoking an MCP grant does not immediately revoke an already issued URL. Partial uploads are aborted on failure, with lifecycle cleanup as a fallback; one-day object expiration is eventual S3 lifecycle cleanup, not a guarantee of deletion within 24 hours.

Every write requires a stable `operation_id`; all existing-message writes require the opaque `expected_version` from a read/create/update result. Scope and active-account checks occur inside the service before backend calls or durable reservations. Verified OAuth binds account, client and credentials into request-local closures, outside tool arguments, results and SDK authInfo.extra. Draft mutations resolve the unique canonical Drafts mailbox. Other message writes use explicit source and destination IDs inside the connected account.

Tool failures include structured `{error:{code,message,retry_after?}}` data with stable sanitized codes such as `upstream_timeout`, `temporarily_unavailable`, `reconnect_required`, `not_found` and `invalid_input`; raw upstream bodies, tokens and exception details are never returned. A `retry_after` hint is included only when the upstream supplied bounded valid integer seconds; the service never invents a delay or automatically retries a search. Read error advice never prescribes write operation IDs. Write receipts keep their existing conservative uncertainty semantics.

Create uses a paired `body:{text,html}`, where null HTML intentionally means plaintext, with optional owned From, reply-to, recipient arrays and base64 attachment additions. Text is bounded to 128 KiB, HTML to 256 KiB and decoded attachments to 2 MiB combined. Inline attachments require unique CIDs. Outbound addresses use the same pinned recipient validator and options as the existing API; malformed entries reject the whole request instead of disappearing. No caller-supplied raw MIME, URLs, storage IDs or arbitrary headers are accepted.

`create_reply_draft` reads an original message during reserved preflight, derives a new canonical Drafts message, and passes the exact same upload/verify/authored-proof flow as ordinary creation. Stable identical operation retries return durable status before fetching the original again; changed input conflicts. Automatic replies prefer external Reply-To, otherwise From; when continuing your own Sent message, they use external original To recipients or reject if none remain. Reply-all adds original To/Cc and excludes the connected account’s exact primary/alias addresses, with case-insensitive deduplication; plus/dot alias guesses are not made. Owned identity metadata is independently bounded to 1,000 case-insensitive unique validated addresses; the final recipient cap remains 100. Explicit `to`/`cc` overrides replace both derived lists, preserve caller intent including self recipients, and never inherit Bcc. The tool never inherits original attachments or source HTML. A new Message-ID and validated In-Reply-To/References preserve reply threading; missing, malformed or oversized threading data fails before upload. Optional `quoteOriginal:true` quotes only complete normalized plaintext, escaping it into paired HTML when supplied, and refuses truncated text or expanded content bounds. Ordinary later draft patches preserve those threading headers.

Editing and sending require durable `mcp_authored` proof for the exact account/mailbox/UID and full-source SHA-256. Only this service’s create/reply/update flow initiates that grade after the uploaded candidate matches all composed MIME bytes. The existing API cannot prove every legacy message’s hidden submission recipients, so legacy or externally changed drafts fail explicitly as `unsupported_content` before upload or send dispatch. Reconnecting OAuth does not upgrade them. Reading, moving, flag/label changes and canonical draft deletion remain independently supported for observed legacy messages. Moves and flag changes carry authored grade only when trusted prior proof and both source hashes match; observing legacy source never upgrades it. A queued Sent result is observed, because submission can change source bytes. Proofs contain digests and references, not a separate encrypted recipient store.

For eligible authored drafts, update is a patch: omitted headers, body and files are preserved; an explicit recipient array clears/replaces only that field, paired body replaces both representations, `deleteAttachmentIds` explicitly removes selected existing files, and `attachments` adds files. Unsupported or unverifiable MIME preservation fails explicitly before mutation. Supported patches preserve ordinary IMAP flags, labels, custom metadata, references, file identities and received `idate`. Preservation restrictions are enforced entirely in MCP using the unchanged API.

Replacement uses staged preparation, upload, strict candidate verification, fresh original-version inspection and then deletion; it is not atomic. Verified completion requires proof of the exact candidate. A partial result reports candidate verification and whether original deletion failed, is unconfirmed, or was not attempted; it is an MCP error requiring review, never success. A verified candidate cannot activate if the original changed or its fresh inspection failed; original_verification_failed reports the latter without claiming a version change. An uncertain result does not claim the original still exists or was deleted. A queued send means queue acceptance, never delivery.

Flag updates support custom IMAP keywords separately from custom labels, including supported Answered/Forwarded semantics. Seen/Flagged booleans cannot contradict keyword aliases. Draft, Deleted and internal label flags cannot be toggled through this tool. Label replacement cannot be mixed with add/remove lists. Backend verification confirms requested changes before a minimal reference/proof receipt; use `read_message` for current complete sets. Identical retries return the historical receipt without refetching or echoing potentially changed state.

Write receipts and account/mailbox/UID guards use the existing DynamoDB table without TTL. They retain intent digests, minimal references/proofs and queue outcomes, never message bodies, recipients, custom flag/label names or tokens. Private operation markers bind uploaded/moved messages to durable activation receipts; raw markers are not public. The shared guard spans OAuth clients. Identical input with the same operation ID retrieves stored status; changed input conflicts. Pending, queued, retired and uncertain fences cannot be reclaimed by age or bypassed with a new ID. Verified flag updates release their same-UID guard atomically; source-retiring operations preserve their fence. After uncertain dispatch, do not resend or change operation ID. Preflight failure releases a guard only together with a durable failed receipt. These fences coordinate this service; the backend exposes no compare-and-swap against external webmail/IMAP changes after inspection.

Search uses a 45-second upstream ceiling, clamped at each dispatch to the live Lambda remaining time minus two seconds, after authentication. CloudFront’s origin-response timeout and Lambda’s request timeout are 60 seconds. Exhausted upstream budgets return explicit timeout advice; ordinary temporary failures do not claim a timeout. Filters are never silently narrowed and searches are not automatically retried. During diagnosis, five roughly ten-second Lambda calls strongly correlated by wall-clock time with backend HTTP 499 responses; this was not an exact request-trace join, and completed backend search latencies still need measurement.

An MCP HTTP abort does not cancel MongoDB queries: underlying Wildduck work may continue past the deadline, so do not automatically retry or immediately repeat broad searches. Timing logs measure HTTP waiting and do not prove that MongoDB work has stopped.

MCP HTTP request bodies are bounded to 5 MiB so supported attachment additions fit. The adapter separately measures full serialized request/response envelopes, including JSON escaping, base64 and metadata, with a conservative 6,000,000-byte safety bound. Oversized requests return 413 before application work; oversized buffered responses return 502 response_too_large without silently dropping fields. AWS may reject an oversized invocation before application code runs. Individual schema bounds do not guarantee that every aggregate combination fits; no labels, attachments or message data are silently dropped to make it fit. After any write error, retain the same operation ID.

## Local validation

Use Node.js 26, Bun 1.4.4 or newer, `zip`, and git-flow:

```sh
bun install --frozen-lockfile --ignore-scripts
bun run validate
bun run dev
```

The local server binds `127.0.0.1:3000`; `PORT` changes the port. With auth configuration absent, `/healthz` reports the package version, `/readyz` and `/mcp` return 503, and no AWS request is made. Configuration is not a credential bypass. `bun run validate` runs Bun's TypeScript checker, Oxlint, tests, bundling and a real Node 26 Lambda-event smoke test. HTTP tests inject a typed test runtime with the real engine/crypto/store contracts and exercise password/TOTP consent, CSRF, redirects, code exchange, refresh and request-scoped MCP identity; production never installs a test verifier.

## Runtime and storage

`PUBLIC_BASE_URL` is a required canonical HTTPS origin for a usable service. Production imports `https://wildduck-mcp.rungie.com` from the administrator-owned bootstrap stack; it is not a GitHub variable. Local development may supply a separate explicit HTTPS test origin. Never derive the issuer from Host or forwarded headers. `DOWNLOAD_BUCKET_NAME` selects the dedicated private temporary-download bucket, imported from bootstrap in production. When absent, inline attachment reads remain available and `get_attachment_download` fails unavailable. `CREDENTIAL_TABLE_NAME` selects the durable state table; `AUTH_KEYRING_PARAMETER` contains only the exact SSM parameter name `/wildduck-mcp/prod/auth-keyring`. No backend credentials or encryption-key values belong in environment variables, CloudFormation, GitHub or source control.

Provision the keyring separately as an SSM **Standard SecureString** under the AWS-managed `aws/ssm` key. Its JSON shape is `{"activeKeyId":"v1","keys":{"v1":"<canonical base64 encoding of 32 random bytes>"}}`, at most four KiB. Use an administrator's approved secret-injection workflow: generate key bytes in memory, send the value through stdin/API request data, and avoid command arguments, files and logs. CloudFormation does not create this SecureString. The runtime can only `ssm:GetParameter` that exact ARN; the CI deployment role cannot read or write its value. No customer-managed KMS key or paid key-management service is added.

Keyring loading is lazy, bounded and cached for at most five minutes. Concurrent loads coalesce; an expired cache fails closed when SSM is unavailable. Each request consults the provider and rebuilds crypto/client services when key material changes. Add a new key and change `activeKeyId` to rotate. Retain old keys while encrypted records, issued tokens and stateless client IDs/secrets depend on them; client registration IDs and secrets do not have an automatic expiration. Removing old keys deliberately invalidates their dependents.

DynamoDB Standard remains provisioned at **exactly 1 RCU and 1 WCU**, with no secondary indexes or autoscaling. The table is retained on deletion/replacement. Its `pk`/`sk` keys use the `wildduck-mcp#` namespace, enforced by runtime IAM. `expiresAt` TTL is eventual cleanup; validity is checked synchronously. Strong reads, conditional transactions, bounded throttling retries and AWS transaction idempotency implement atomic codes and refresh rotation. Concurrent bursts can still throttle this deliberately tiny table. Backend credentials and retry receipts are encrypted with AES-GCM, purpose-separated keys and account/generation-bound authenticated context. Mail remains in Wildduck.

Lambda uses Node 26 preview, ARM64, 1024 MB, a 60-second request timeout and 14-day logs. Preview availability in the intended region is an accepted deployment constraint. Health is liveness; `/readyz` checks configured key availability. Neither is proof of a real account login or successful client interoperability. MCP uses the official stateless JSON transport and passes verified request identity through `authInfo` into tool context. Only the fifteen mail tools are registered; no profile, connection-status, service-information or inbox-subject helper remains. Upstream credentials stay inside request-local bound closures, outside SDK tool arguments/results and `authInfo.extra`.

## Deployment and rollback

Main and develop pushes and their pull requests validate and build. The main-only deployment job uses short-lived GitHub OIDC credentials and deploys the exact verified artifact. Bootstrap IAM is administered separately; CI cannot edit IAM. Trust pins the immutable owner/repository IDs and main branch. No long-lived AWS access key is stored in GitHub.

An administrator can create/update the bootstrap stack using `infra/bootstrap.yml` and `CAPABILITY_NAMED_IAM` in the intended region. It expects the existing `GitHubOIDCProvider-Arn` and `CertificateAccepterLambda-Arn` exports. Inspect its outputs and configure repository variables `AWS_DEPLOY_ROLE_ARN`, `AWS_DEPLOYMENT_BUCKET_NAME`, and `AWS_EXECUTION_ROLE_ARN`. Provision the SecureString separately, then set `AUTH_KEYRING_PARAMETER=/wildduck-mcp/prod/auth-keyring` and update bootstrap with the existing Function URL origin as its `FunctionUrlOrigin` parameter. Set `SERVERLESS_ACCESS_KEY` as a repository secret through the normal secret UI/stdin, and `DEPLOY_ENABLED=true` last.

The bootstrap creates a stable CloudFront distribution, two challenge-header policies and A/AAAA records for the approved `wildduck-mcp.rungie.com` hostname in the existing hosted zone. It mirrors the `webservices` certificate/DNS conventions: `Custom::DNSCertificate` invokes the existing shared provider in the stack region to provision an ACM certificate in `us-east-1`, and Route 53 aliases point to the distribution. No `www` alias is needed. It also mirrors `apartment-manager` production retention and the existing HTTP/2+HTTP/3, IPv6 and PriceClass_100 configuration. Unlike their static sites, all OAuth paths disable caching and forward authorization, Origin, cookies and query strings. The native bootstrap stays self-contained so administrators can deploy it directly without an include macro or template-composition service.

The hostname is known before resource creation, so both challenge policies and the exported canonical origin use the same hostname parameter. The distribution’s origin is a plain existing Function URL origin parameter, never a cross-stack reference back to Lambda. This avoids a circular dependency and needs no generated-hostname activation phase. Update bootstrap first, then deploy the application that imports `wildduck-mcp-prod-public-origin`. The attachment enhancement additionally requires the bootstrap-created private download bucket and runtime IAM before service deployment: its export supplies `DOWNLOAD_BUCKET_NAME`, and runtime S3 object permissions are limited to its `downloads/` prefix. The runtime additionally has `s3:ListBucket` on this dedicated download bucket so a missing object’s HEAD returns an authoritative 404; the service exposes no listing tool and performs no S3 listing request. CI does not provision the bucket or edit these IAM permissions. CI has no CloudFront, DNS, certificate-provider invocation or bootstrap-stack mutation permissions.

For this existing-deployment migration, obtain the Function URL from the current `ApiLambdaFunctionUrl` stack output, remove its trailing slash, and pass that public origin explicitly:

```sh
aws cloudformation deploy --region us-west-2 \
  --stack-name wildduck-mcp-bootstrap --template-file infra/bootstrap.yml \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides "FunctionUrlOrigin=$FUNCTION_URL_ORIGIN"
```

Before bootstrap mutation, verify the exact DNS name and existing CloudFront alias ownership. Wait for certificate validation, distribution deployment and DNS readiness; then deploy and verify the application’s canonical origin. Preserve the Function URL origin parameter on later bootstrap updates (or use `UsePreviousValue` with the update-stack API), and update it explicitly if Lambda’s Function URL is ever recreated. The existing certificate validation CNAMEs must remain for ACM renewal.

Local `bun run package` keeps the canonical-origin import unresolved and uses explicit infrastructure placeholders without real keys or AWS access. `bun run deploy` refuses missing settings and unexpected parameter names. For an authorized deployment, validate first and inject the same settings using normal credential tooling. Never deploy placeholders directly with raw Serverless commands.

Live deployment verification checks the package version, ready key loading, actual standard Bearer/Basic 401 challenge headers, CORS exposure and the discovery issuer/resource. An in-memory confidential registration must successfully authenticate a fabricated-token revocation with Basic credentials while missing/wrong credentials fail, verifying that CloudFront forwards Authorization. It also registers a stateless synthetic native client and cancels the login page using its encrypted cookie and CSRF token, testing the gateway’s query/form/cookie/redirect behavior without account credentials or a database write. It does not log in a real account. Real-account connection/reconnection and Claude, ChatGPT, Codex, Dot and Duet interoperability remain acceptance checks to perform after reviewed provisioning/deployment. A valid OAuth grant does not override a host's action-approval policies.

Published Lambda versions and the previous artifact permit operator rollback. Restore the previous reviewed release/configuration and verify health/version, discovery and readiness; do not use `serverless remove` as rollback. Retain encryption keys required by surviving records and clients. The retained table and versioned artifact bucket outlive stack deletion. The CloudFront distribution, its dependent header policies and certificate are retained; eventual removal is a separate ordered administrative cleanup. Preserve ACM validation records for renewal. The temporary-download S3 bucket uses AES256 encryption, public-access blocking, HTTPS-only access and eventual lifecycle cleanup. No API Gateway, edge function, WAF, extra log group, new KMS key, index or autoscaling resource is added. The Function URL remains the CloudFront origin; connect clients using the canonical hostname. A previous release rollback must restore its matching origin configuration as well as its artifact.

CloudFront uses AWS’s managed `CachingDisabled` and `AllViewerExceptHostHeader` policies. All seven supported methods pass through; HTTPS is required at both hops. Configurable CloudFront error-cache TTLs are zero, with no error-body/status rewriting. HTTP 401 is not a configurable custom-error status. The two response-header policies add Bearer discovery by default and Basic challenges on exact `/token` and `/revoke` paths. They preserve any original standard challenge (`Override: false`) and do not overwrite CSP, referrer policy, cookies or CORS. Static challenges also appear on successful responses; future dynamic insufficient-scope challenges require revisiting this edge behavior.

CloudFront’s [ongoing free allowance](https://aws.amazon.com/cloudfront/pricing/pay-as-you-go/) includes ten million HTTP/HTTPS requests and one TB of outbound transfer monthly. The allowance is shared across the account/organization, and its remaining usage has not been assumed here; usage outside allowances and ancillary transfer/features can incur charges. This uses the existing hosted zone and shared certificate provider, with no new hosted zone or paid certificate service. Lambda and DynamoDB retain their existing billing and capacity.

## Branches and releases

`develop` is the default development branch and `main` is the deployed branch. Tags are bare package versions. Initialize with `bun run gitflow:init`. From clean develop, `bun pm version patch --no-git-tag-version` (or npm equivalent) invokes the postversion workflow: update lockfile, validate, commit, finish a Gitflow release and merge main back into develop. Nothing pushes automatically. Inspect status before recovering any failed release. `bun run test:release` exercises the release path in a disposable local repository.

Release 0.2.1 exposed a live Function URL limitation: AWS remaps `WWW-Authenticate`, blocking standard OAuth discovery despite correct local responses. This CloudFront migration requires reviewed bootstrap and application deployment plus actual public-header, cookie and browser acceptance; local packaging alone does not prove AWS wire compatibility. The MCP-only preservation implementation has passed local validation and independent safety review. Main pushes deploy through CI; real-account mail acceptance remains unverified. No Wildduck server deployment, patch or restart is required or authorized. Real-account writes are untested; local tests performed no real mail writes or sends.
